# Issue Splitter Rules

## 목적

한 문장에 섞인 금융상품과 문제를 독립적인 민원 사건으로 분리한다.

사용자는 대부분 여러 문제를 한 번에 이야기한다. 이걸 분리하지 않고 다음 단계(Focal Builder, RAG, Logic Verification)로 넘기면, 서로 다른 규정과 증빙이 하나의 판단으로 섞여버려 결론이 부정확해진다. Issue Splitter는 파이프라인의 첫 단계이므로, 여기서 생긴 오류는 뒤로 갈수록 커진다 — 잘못 나뉘거나 잘못 합쳐진 issue는 이후 어떤 단계에서도 복구되지 않는다.

## 분리 기준

- **해결하려는 조치가 다르면 분리한다.**
  같은 문장 안에 있어도 사용자가 원하는 결과가 다르면 별개의 민원이다. (예: "이자 재정산해달라" vs "수수료율을 확인해달라")
- **중심 계약·거래·통지서가 다르면 분리한다.**
  참조하는 계약서·거래·안내문 자체가 다르면, 사실관계를 검증할 근거 문서도 달라지므로 분리한다.
- **적용 규정 또는 필요한 증빙이 다르면 분리한다.**
  같은 계약이라도 한쪽은 우대금리 약정 위반, 다른 쪽은 수수료 고시 불일치처럼 검토해야 할 조항과 준비할 서류가 다르면 분리한다.
- **같은 사건의 원인과 결과는 하나의 민원에 유지한다.**
  "시스템 오류로 인출이 안 됐고, 그래서 이체도 못 했다"처럼 하나의 원인에서 파생된 결과는 나누지 않는다. 나누면 오히려 인과관계가 끊겨서 판단이 왜곡된다.
- **상품명만 다르고 같은 거래라면 성급하게 분리하지 않는다.**
  상품명이 다르더라도 계약·조치·근거가 전부 같으면 분리하지 않는다. 반대로 상품명이 같아도 계약·조치·근거가 다르면 분리한다 — 상품명은 분리 여부를 판단하는 기준이 아니다.

## 분류 우선순위

1. 사용자의 명시적 문제
2. 사건·거래·계약의 구분
3. 상품
4. 요청한 해결 조치

이 순서는 판단이 애매할 때 어느 기준을 먼저 볼지 정하는 우선순위다. 사용자가 명시적으로 말한 문제가 가장 우선이고, 상품명은 세 번째로 밀린다 — 상품명만 보고 쟁점을 추측하지 않는다. 예를 들어 상품은 같은데(정기예금) 사용자가 말한 문제가 둘(우대금리, 수수료)이면, 1번 기준(명시적 문제)에 따라 분리 방향으로 먼저 검토하고, 그다음 2번 기준(계약 동일 여부)으로 다시 확인한다.

## 판단 예시

**입력**
> "KB 정기예금에 작년 3월 10일 1년 만기로 가입했는데, 우대금리 3.5%가 아니라 기본금리 2.1%로만 이자가 계산됐어요. 그리고 별개로 중도해지 수수료율이 가입할 때 안내받은 것과 창구에서 안내받은 게 달라요."

**분리 기준 대입**
| 기준 | 판단 | 근거 |
|---|---|---|
| 해결하려는 조치가 다른가? | YES | 이자 재정산 요청 vs 수수료율 확인 요청 |
| 중심 계약·거래가 다른가? | NO | 동일한 정기예금 계약 1건 |
| 적용 규정·증빙이 다른가? | YES | 우대금리 조건표 vs 중도해지 수수료 고시 |
| 같은 사건의 원인과 결과인가? | NO | 금리 미적용과 수수료 안내 불일치는 서로 무관한 별도 쟁점 |

**결론**: 계약은 같지만(NO) 조치와 근거가 다르므로(YES, YES) → 2개 issue로 분리하고, 두 issue의 `shared_context_refs`에 동일한 계약 참조값을 남긴다. 계약이 같다는 사실 자체는 두 issue를 합치는 이유가 아니라, 두 issue가 같은 배경을 공유한다는 참조 정보로만 남는다.

## 출력

```json
{
  "issues": [
    {
      "issue_id": "issue_001",
      "product": "예금",
      "issue_type": "인출제한",
      "text_span": "...",
      "requested_remedy": "...",
      "shared_context_refs": []
    }
  ],
  "unresolved_parts": []
}
```

### 출력 필드 설명

- `issue_id`: 문의 내에서 issue를 순번대로 식별하는 값. 이후 모든 단계(Focal Builder, RAG, Decision Gate)가 이 값으로 issue를 추적한다.
- `product`: 사용자가 언급한 상품명. 분리 판단의 근거가 아니라 결과를 기록하는 값이라는 점에 유의한다.
- `issue_type`: 이 issue가 어떤 종류의 문제인지 나타내는 짧은 분류명. 사람이 읽고 바로 이해할 수 있는 표현을 쓴다.
- `text_span`: 원문에서 이 issue에 해당하는 부분을 그대로 발췌한다. 요약하거나 다듬지 않고 원문 표현을 유지해야, 이후 단계에서 원문과 대조 검증이 가능하다.
- `requested_remedy`: 사용자가 원하는 해결 방향. 아직 확정된 조치가 아니라 사용자가 요청한 내용이라는 점을 명확히 한다.
- `shared_context_refs`: 다른 issue와 공유하는 배경(계약·거래 등)의 참조값. 두 issue를 하나로 합치지 않으면서도 서로 연결된 배경이 있음을 남기는 용도다.
- `unresolved_parts`: 분리 기준을 적용할 수 없어 판단을 유보한 원문 조각. 비어 있지 않으면 이후 Decision Gate에서 `ask`로 이어질 가능성이 높다는 신호다.

## 실패 처리

- **문장 하나를 임의로 여러 민원으로 쪼개지 않는다.** 분리 기준 중 어느 하나도 명확히 다르다고 판단할 근거가 없으면, 쪼개는 대신 하나의 issue로 유지한다. 애매함을 분리로 해소하려 하지 않는다.
- **분리 기준이 불명확하면 `unresolved_parts`에 남기고 `ask`를 제안한다.** 이 경우 Issue Splitter가 스스로 결론을 내리지 않고, 판단에 필요한 정보가 부족하다는 사실 자체를 다음 단계에 넘긴다.
- **복합 민원의 각 issue에 원문 span을 남긴다.** 요약이나 재구성된 문장이 아니라 원문 그대로여야 하며, 이는 이후 단계가 원문을 다시 참조할 수 있도록 하기 위함이다.
- **상품명만 다르고 나머지가 전부 같은 경우, 상품명을 근거로 분리하지 않는다.** 이는 "상품명만 보고 쟁점을 추측하지 않는다"는 원칙의 실패 방지 규칙이며, 분류 우선순위 3번(상품)이 1·2번(명시적 문제, 계약·거래 구분)보다 뒤에 있는 이유이기도 하다.
- **issue 수가 원문에 언급된 문제 수보다 많거나 적으면 원인을 점검한다.** 언급되지 않은 issue가 생성되었다면 과도한 분리이고, 언급된 문제가 하나의 issue에 뭉쳐 있다면 과소한 분리다. 두 경우 모두 분리 기준을 다시 대입해 확인한다.
