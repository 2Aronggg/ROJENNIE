# 구현 과정과 시행착오

이 문서는 현재 구조가 왜 이렇게 되었는지 설명합니다. 새 기능을 추가할 때 이미 폐기한 방향을 다시 도입하지 않기 위한 기록입니다.

## 1. 구조 변경

### 복합 문의 분해

처음에는 보험·대출·예금별 에이전트를 각각 두는 구조를 검토했습니다. 실제 처리에는 상품별 분리보다 사용자의 문의를 독립 쟁점으로 나누고, 각 쟁점의 사실·근거·결정을 연결하는 것이 더 중요했습니다.

현재는 다음처럼 Case Builder 내부 단계로 통합했습니다.

~~~text
Case Builder
  ├─ Issue Splitter
  ├─ Focal Builder
  ├─ 필수 사실 추출
  └─ 금융상품 연결
~~~

분리된 쟁점은 Evidence & Decision 단계에서 독립적으로 처리하고 마지막에 리포트로 합칩니다.

### 대출 범위 변경

대출은 초기에 구현 밖으로 두었지만 대출 데이터 확보 후 정식 지원 상품으로 포함했습니다. 라우터, 가상 금융정보, Finance MCP, 상품별 RAG 필터, 리포트에 대출 경로와 필수 필드를 추가했습니다.

필수 대출 사실:

~~~text
상품명·대출원금·실행일·만기일
적용금리·금리 유형·잔액·상환 방식
상환 내역·금리 변경 이력·금리 안내 이력·연체 여부
~~~

### 트리 UI 변경

초기 화면에서는 RAG 검색 후보를 page:1, 제19조 같은 노드로 만들었습니다. 검색 후보는 사용자의 사실이나 시스템 판단이 아니므로 민원 트리를 오염시켰습니다.

현재 원칙:

~~~text
트리: 민원·사실·계산·결정
리포트: 판단 이유·근거 문서·조항·페이지·링크
~~~

근거 자료는 리포트에서 클릭해 상세 확인합니다. 노드 확대는 Detail Drawer를 사용해 전체 레이아웃이 흔들리지 않도록 했습니다.

### 이미 입력한 정보 재질문 문제

초기 상담 흐름은 Mock 데이터나 최초 민원에 이미 있는 금액·금리도 다시 물었습니다. 현재는 문의와 내 금융정보를 먼저 합친 뒤 둘 다 없는 핵심 값만 질문합니다.

예를 들어 사용자가 실제 입금액과 적용금리를 모른다고 해도 시스템은 가상 금융정보에서 실제 지급액 279,180원, 가입금액 1,000만원, 적용금리 3.3%를 먼저 보여주고 예상 금액만 질문합니다.

금액 표현이 2천만원처럼 원금인지 예상 이자인지 모호할 때는 바로 확정하지 않고 두 의미를 명시해 재확인합니다.

### 결정 상태와 리포트 불일치

한때 계산 결과는 생성되었는데 UI는 계속 추가 정보 필요 또는 검토 대기로 표시되는 문제가 있었습니다. LLM 응답 문구와 정책 게이트의 결정 상태가 따로 움직였기 때문입니다.

현재는 decision_gate.py에서 상태를 최종 확정하고, 리포트는 그 상태와 근거를 설명합니다. LLM이 다른 상태를 말해도 정책 게이트 결과가 우선입니다.

## 2. 데이터와 RAG 문제

### 파일 형식

초기 ingest는 PDF와 법령 API JSON 중심이었습니다. HWP를 그대로 넣으면 빈 chunk나 깨진 근거가 생길 수 있어 판례·약관 HWP는 필요한 필드를 추출해 CSV로 변환한 뒤 원본과 분리했습니다.

목적별 corpus:

~~~text
regulations.jsonl
products.jsonl
cases.jsonl
glossary.jsonl
all.jsonl
~~~

### null embedding

모든 chunk에 임베딩을 넣으려 했지만 비용·실행환경·모델 의존성이 커졌습니다. 현재는 IDF 가중 전문 검색과 다중 질의 RRF를 기본으로 사용하고, 임베딩이 있는 chunk만 cosine 점수를 보조로 사용합니다.

embedding이 null인 것은 데이터 손상이 아니라 선택적 벡터 검색 상태입니다. 검색 정확도 개선이 필요할 때 운영 환경에서 임베딩을 일괄 생성하고 모델 버전을 고정합니다.

### effective_from / effective_to

법령 API와 달리 PDF·상품설명서는 원문에 시행기간이 없거나 수집 메타데이터가 부족한 경우가 많아 날짜가 null로 남았습니다.

개선 원칙:

1. 법령 API의 시행일과 개정 이력 우선
2. 다음 버전 시행일을 확인한 경우 이전 버전 종료일을 하루 전으로 계산
3. 근거 없는 날짜를 임의로 만들지 않음
4. 계약일과 문서 시점이 맞지 않으면 검토 대기

### 후보 자료 노출 방식

검색 후보는 최종 근거가 아닙니다. 상품·사건 시점·조항·문서 유형을 확인한 뒤 확정 근거로 승격합니다. 사용자 화면에는 문서명·문서 유형·조항·페이지·시행일·원문 링크·짧은 인용만 제공합니다. 검색 점수와 내부 chunk ID는 숨깁니다.

### complaints와 dictionary

민원 데이터는 실제 표현을 배우고 쟁점을 분류하는 데 유용하지만 법적 판단 근거는 아닙니다. routing·평가 corpus로 사용합니다.

dictionary는 법령·금융 용어를 쉬운 말로 보여주는 용도입니다. 결정 근거로 사용하지 않고 완료 리포트 오른쪽에서 어려운 단어를 눌렀을 때 표시합니다.

## 3. 외부 연동 결정

### AIHub MCP를 사용하지 않은 이유

AIHub MCP는 데이터셋 메타데이터 확인용입니다. 데이터셋을 직접 내려받아 data/에 보관하고 로컬 corpus를 만들고 있으므로 런타임 답변에는 필요하지 않습니다.

### Finance MCP를 사용한 이유

Finance MCP는 현재 사용자 금융정보를 에이전트가 일관된 Tool 인터페이스로 조회하도록 만든 계층입니다. 실제 은행 API가 없어도 같은 호출 계약으로 Mock Bank를 연결할 수 있습니다.

읽기 전용 Tool만 제공하며 고객·계좌 소유권은 서버가 검사합니다. 쓰기 Tool과 실제 은행 연동은 없습니다.

### Supabase를 뒤로 미룬 이유

현재 데모의 핵심은 민원 분석과 근거 연결입니다. 먼저 로컬 SQLite로 API·데이터 계약을 고정하고, 여러 사용자와 영구 사례 저장이 필요할 때 Supabase 또는 다른 DB를 붙이기로 했습니다.

현재 SQLite는 `server/finance/mock_bank.sqlite3`이며, 실제 은행 DB가 아니라 `CUST-001`의 가상 고객·예금·적금·대출·거래·상환 데이터를 저장합니다. 에이전트는 SQLite를 직접 읽지 않고 `Finance MCP`의 읽기 전용 Tool을 통해 조회합니다. `mock_data.py`의 기본 데이터를 기준으로 시작 시 가상 데이터가 보장되므로 데모 재현성이 있습니다.

로컬 단일 프로세스 데모만 보면 지금 당장 Supabase가 필수는 아니지만, 서비스를 실제 배포할 예정이라면 Supabase를 다음 단계로 연결해야 합니다. 다만 모든 데이터를 한 번에 옮기지 않고 앱 상태부터 분리합니다.

- Supabase: 사용자·인증·동의 상태, 민원·리포트·검토 결과, 감사 로그
- SQLite 유지: 현재 가상 금융 원장(읽기 전용 데모 데이터)
- 별도 유지: RAG 원천 문서와 corpus

배포 시에도 에이전트는 Finance MCP Tool만 호출하고, 저장 구현만 교체합니다. 이 경계를 유지하면 Supabase 연결이 에이전트 로직 전체 수정으로 번지지 않습니다.

현재 한계:

- Mock Bank는 로컬 파일
- 서버 사례 저장소는 메모리
- 클라이언트 최근 사례는 localStorage
- 서버 재시작 후 사례의 서버 조회는 유지되지 않음

| 증상 | 원인 | 현재 대응 |

| page:1, 제9조가 트리에 보임 | RAG 후보를 사실 노드처럼 생성 | 후보를 리포트 근거 카드로 이동 |

| AIHub 인증 실패·502 | 다운로드 권한·파일키·셸 환경 문제 | 데이터셋 권한과 파일키를 별도 확인 |

## 5. 보안·품질 원칙

검색 문서는 명령이 아니라 참고 데이터로 취급합니다. HTML script·hidden text·comment는 제거하고, 검색 결과가 외부 URL을 자동 호출하거나 DB 쓰기를 수행하지 않게 합니다.

LLM 호출은 server/policy/gateway.py를 통과합니다.

- 입력 개인정보 마스킹
- 허용된 호출 단계만 실행
- 출력 개인정보 재검사
- JSON 구조 확인
- 원문 없이 해시·메타데이터만 감사 로그

사람에게 넘겨야 하는 상황:

- 검색 근거 없음
- 문서 충돌
- 적용 시점 불명확
- 배상·분쟁·소송 가능성
- 보이스피싱·금융사고 의심
- 민감한 신용정보
- 고객이 공식 민원을 요구

평가에서는 단순 정답률보다 근거 없는 단정률, 과거 약관 적용 오류율, 숫자·금리·날짜 오류율, 잘못된 배상 안내율, 상담원 이관 누락률, 개인정보 노출률을 별도로 봅니다.

## 6. 현재 다음 작업

1. 배포 전 Supabase에 사용자·민원·리포트·검토·감사 로그 연결
2. 계약일·거래일 기반 문서 버전 필드 보강
3. 대출·예금·적금 회귀 평가 케이스 확대
4. 근거 인용 정확도와 상충 문서 테스트
5. 필요할 때만 임베딩 일괄 생성

여러 에이전트를 더 추가하기보다 현재 Case Builder → Evidence & Decision → Policy Gate → Response 흐름의 관측성·평가·데이터 품질을 먼저 개선합니다.
