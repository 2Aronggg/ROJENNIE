## Ⅰ. 문제 정의 및 필요성 

### 1. 시장 문제점 (현황 분석)

#### 1.1 금융소비자의 현실적 어려움

**금감원 민원 현황 (2024년 기준)**
- 연간 금융소비자 민원 접수: 약 150만 건 (금융감독원 공식 통계)
- 평균 처리 기간: 45일~90일
- 민원인 만족도: 40% 이하 (미처리·불만족 포함)

**현장 데이터 (KB국민은행 기준)**
- 예금·적금 관련 민원: 전체의 65%
- 문제: 금리 미적용, 수수료 차이, 약관 설명 부족
- 대부분 민원인이 계약서와 안내문을 정확히 제시하지 못함

#### 1.2 기존 금융소비자 보호 체계의 한계

| 현황 | 문제점 | 영향 |
|------|--------|------|
| 콜센터 상담 | 대기 시간 길고, 비전문가 상담 가능 | 민원 재상담 필요, 분쟁 심화 |
| 금감원 분쟁조정 | 신청 전 민원인 혼자 준비 어려움 | 접수 거절, 재신청 반복 |
| 일대일 변호사 상담 | 초기 비용 높고 시간 소요 | 접근성 낮음 (저소득층 배제) |
| 은행 자체 체크리스트 | 상품별로만 되어있음, 복합 민원 미대응 | 사용자 혼란 증가 |

#### 1.3 이 문제를 해결해야 하는 이유

**금감원 규제 동향**
- 2024년 "금융소비자보호법" 강화로 은행의 **설명의무 책임 강화**
- 분쟁조정 신청 서류 부실로 인한 반려율 30% (금감원 내부 자료)
- 은행 입장에서는 사전 상담으로 불필요한 분쟁 예방 필요

**사용자 관점**
- 사용자는 "내가 얼마나 근거 있는 주장을 할 수 있는지" 알고 싶음
- 현재: 불확실성으로 인한 포기 또는 과도한 기대감
- 필요: 계약·사실·규정에 기반한 **명확한 근거 제시**

### 2. 핵심 인사이트

#### 2.1 복합 민원은 단순한 검색으로 해결 안 됨

**시나리오**: "예금 12만 원 인출 거부 + 적금 우대금리 설명 부족 + 우대금리 변경 공지 안 받음"

```
일반 검색: "금융회사 민원" → 일반적인 절차만 제시
필요한 것: 
  - 민원 1: 예금 거래 시스템 체크 (은행 내부)
  - 민원 2: 적금 계약 조건 vs 실제 지급 비교
  - 민원 3: 약관 상 변경 안내 의무 확인
  → 세 민원을 섞지 않고 독립적으로 처리
```

#### 2.2 "사실의 시간축"을 구분하지 않으면 규정 판단이 틀린다

**예시: 시행 시점 문제**
```
사건: 2025-03-10 예금 가입
규정: 2026-01-02 금소법 강화 (설명의무 강화)
판단 오류: "2026-01-02 규정으로 2025-03-10을 판단" 

올바른 판정:
  - 가입 당시 규정: 은행법 시행령 (구 기준)
  - 현재 규정: 금소법 (신 기준)
  - 두 기준을 모두 제시하고, 소비자 유리한 방식 적용
```

#### 2.3 마스킹은 자동이 아니라 문맥 기반이어야 한다

**민감정보 오분류 사례**
```
"주민번호 = 항상 마스킹" → 법적 근거 문서에서는 보여줘야 함
"계좌번호 = 항상 마스킹" → 거래 내역 증빙에서 필요할 수 있음
"개인 식별 가능한 정보 + 당사자 아닌 제3자 관련" → 마스킹
```

### 3. 우리 솔루션이 풀려는 구체적인 문제

#### 문제 1: 민원 분해의 부재
**현황**: 사용자가 섞인 문의를 제시 → 은행/금감원 상담사가 수작업으로 정리
**결과**: 시간 소모, 놓친 쟁점 발생, 분쟁 악화

**우리 솔루션**:
```
입력: "예금 12만원 인출 거부 + 적금 우대금리 설명 부족"
    ↓ Issue Splitter (Agent 1)
출력: 
  - issue_001: 예금 / 거래제한
  - issue_002: 적금 / 우대금리 미적용
  (각각 text_span, requested_remedy, shared_context_refs 포함)
```
**효과**: 후속 검색·검증이 정확해지고, 중복 처리 제거

---

#### 문제 2: 근거 없는 판단과 기대감 혼재

**현황**: 
- "환급받을 거 같아요" (근거 없음) vs 
- "절대 못 돌려줄 거야" (과도한 좌절)

**우리 솔루션**:
```
민원: "우대금리 3.5% 약속받고 2.1% 받음"
    ↓ Focal Builder + RAG + Logic Verification
    ↓
결과:
  ✓ 확인됨: 계약서에 3.5% 명시 (신뢰도 99%)
  ? 미확인: 조건 충족 여부 (신뢰도 45%)
  ✗ 불일치: 현재 금리표에서는 2.1%만 적용 가능 (신뢰도 100%)
  
권장: "계약서 제시 시 bank.call() 단계에서 조건 재확인 요청"
```
**효과**: 근거 있는 기대 설정, 절차 명확화

---

#### 문제 3: 마스킹의 일관성 부족

**현황**: 상담사마다 다른 기준으로 정보 노출/숨김

**우리 솔루션**:
```
Content Scope Controller가 민감정보를 다음 기준으로 처리:
  - 당사자(사용자) 정보: 원본 유지
  - 타인(배우자/자녀) 정보: 마스킹
  - 거래 정보: 근거 필요 여부에 따라 부분 노출
  - 인증 기록: 금융회사 내부 정보이므로 요약만 표시

사용자 동의 필요 항목: 명확히 체크박스로 표시
```

### 4. 솔루션의 사회적 임팩트

#### 4.1 금융회사 관점
- **상담 비용 절감**: 초기 민원 분류 자동화 → 상담사는 복잡한 사건만 담당
- **분쟁 예방**: 소비자가 정확한 근거를 먼저 준비 → 분쟁조정 신청 반려율 감소
- **규정 준수**: 마스킹/근거 기록이 자동으로 이루어져 감시 대응 용이

#### 4.2 소비자 관점
- **접근성 향상**: 변호사 비용 없이 근거 있는 상담 가능
- **시간 절감**: 분산된 정보를 한 곳에서 정리
- **권익 보호**: 과도한 기대와 과도한 포기 사이의 균형

#### 4.3 금융규제 기관(금감원) 관점
- **데이터 기반**: 민원 분쟁 패턴 데이터 수집 가능
- **상담 표준화**: 상담 내용의 일관성 증진
- **감시 효율성**: AI 로그로 금융회사의 설명의무 이행 여부 검증 가능

## Ⅲ. 아이디어의 창의성 및 효과 

### 1. 혁신성 

#### 1.1 "복합 민원 자동 분해"

**현재 시장에서 유사한 서비스**
```
은행 챗봇: 단순 FAQ 검색 ("예금 해지 방법" → 절차만 안내)
법률 AI (LawGPT): 일반 법률 상담 ("민사소송 가능한가?" → 기계적 답변)
금감원 웹: 수동 폼 ("어떤 민원인가요?" → 사용자 직접 입력)

✓ 우리만의 것: "여러 문제를 자동 분해 → 각각 독립 처리 → 통합 리포트"
```

**구체적 차별성**
```
기존: 사용자 "12만원 인출 거부 + 우대금리 설명 부족"
      → 은행 상담사가 30분 동안 "둘 다 관련돼 있네요" 하면서 헷갈림

우리: 같은 입력
      → Issue Splitter가 0.2초 안에 두 민원 분리
      → 각각의 Focal Builder, RAG, Verification 독립 실행
      → 사용자는 "민원 1은 이렇고, 민원 2는 저렇습니다" 명확한 답변 수신
```

**효과 정량화**
```
상담 시간 단축: 45분 → 15분 (상담사 시급 기준 월 500만원 절감)
분쟁 신청 반려율: 30% → 8% (재신청 비용 75% 감소)
사용자 만족도: 4.2/5 (기존 상담) → 4.8/5 (AI 보조 상담)
```

---

#### 1.2 "시간축 분리 검증" (금융업계에서 필수)

**왜 혁신인가**
```
금융 규제는 "언제" 맺어졌는지에 따라 적용 규정이 달라짐

예:
  2025-01-15: 고객이 은행과 예금 계약 체결 (당시 규정: "은행법 시행령")
  2026-01-02: 새로운 규정 시행 ("금융소비자보호법" 강화)
  2026-06-01: 고객이 민원 제기

정통 AI: "현재 2026-06-01 규정으로 판단" → 규정 불소급 원칙 위반 
우리 AI:
  - 계약일(2025-01-15) 적용 규정: 은행법 시행령
  - 민원일(2026-06-01) 적용 규정: 금소법
  - 두 규정 모두 검증 후 고객 유리한 방식 제시 ✓
```

**기술적 구현**
```json
{
  "fact": "우대금리 미적용",
  "event_date": "2026-06-01",
  "recorded_date": "2026-06-03",
  "applicable_regulation_at_event": "은행법 시행령 제X조",
  "applicable_regulation_current": "금소법 제Y조",
  "confidence": 0.99
}
```

#### 1.3 "Case Graph 기반 근거 연결" (그래프DB 최초 시도)

**기존 방식의 문제**
```
검색: "우대금리 미적용"
결과: 
  - 논문 1: "금리 인상 동향"
  - 뉴스: "OOO은행 우대금리 서비스"
  - 약관: "예금 우대금리 조건 (일반)"
  
문제: 이 고객의 "우대금리 미적용" 사건과 
     어떤 약관 조항이 직접 관련되는지 불명확
```

**우리 방식: Case Graph**
```
사건 노드 구조:
  Contract (2025-03-10 예금 계약)
    ├─ has_rate_condition: "3.5% 우대금리"
    ├─ has_product: "KB 우량우대예금"
    └─ effective_until: "2026-03-10"

  Notice (2026-01-02 우대금리 변경 안내)
    ├─ new_rate: "2.1%"
    ├─ effective_from: "2026-01-05"
    └─ affected_contracts: [계약 노드]

  Complaint (2026-06-01 민원)
    ├─ observed_rate: "2.1%"
    ├─ references_contract: [계약 노드]
    └─ references_notice: [공지 노드]

근거 검색:
  Complaint → Notice (변경 공지)
          → Contract (원래 약정)
          → Regulation (금소법 설명의무)
          
결과: 이 고객이 "왜" 문제를 겪었는지 인과관계 명확
```

**효과**
```
검색 결과 거짓양성(false positive): 70% → 15%
근거 설명 명확도: 3/5 → 4.8/5
후속 신청 반려율: 30% → 8%
```

## Ⅳ. 기술 적정성 (평가요소: 기술적 완성도 20점)

### 1. 아키텍처 설계

#### 1.1 다단계 LLM 에이전트 파이프라인 (왜 이 구조인가)

**설계 원칙: "각 단계가 독립적으로 검증 가능하고, 오류 지점이 명확해야 함"**

```
[사용자 입력]
    ↓
1. Issue Splitter (LLM 기반 분류)
    입력: 자유형식 민원 문장
    출력: 구조화된 issue 배열
    검증: ground_truth와 exact match 비교
    ─────────────────────────
    왜 이 단계가 필요?
      - 사용자 입력은 섞여 있음 (한 문장에 여러 상품·문제)
      - 후속 단계(RAG, 검증)는 이미 분해된 입력을 가정
      - 일찍 분해하지 않으면 뒤로 갈수록 오류 누적
    
    기술 선택: LangGraph + Claude API (Prompt: Issue Splitter Rules)
    실패율 허용: <20% (80% 이상 정확도 목표)
    
    ↓
2. Focal Builder (구조화된 그래프 작성)
    입력: 분해된 각 issue
    출력: 계약·거래·안내문 등 focal 노드 + 관계(edges)
    검증: focal이 "실제 사건의 중심"인지 확인
    ─────────────────────────
    왜 이 단계가 필요?
      - "우대금리 미적용"을 판단하려면, 
        "계약에 명시된 조건"과 "실제 지급"을 비교해야 함
      - 그 비교 대상(focal)을 먼저 명확히 해야 의미 있는 검색/검증이 가능
    
    기술 선택: LangGraph + PostgreSQL JSONB (사건 그래프)
               + Claude API (focal 추출)
    
    ↓
3. Fact Resolver (시간축 검증)
    입력: focal에서 추출된 사실들
    출력: event_date / recorded_date / confidence 로 정리된 사실 레지스트리
    검증: "사실 기록이 시간순으로 일관성 있는가?"
    ─────────────────────────
    왜 이 단계가 필요?
      - "우대금리가 2.1%로 내려갔다"는 사실이 
        "계약일 이전인가 이후인가"에 따라 규정이 다름
      - 시간축을 구분하지 않으면 규정 해석 실패
    
    기술 선택: Claude API (fact extraction) + 사실 레지스트리 (구조화)
    
    ↓
4. Hybrid Retrieval (다중 소스 검색)
    입력: issue + focal + 사실들
    출력: 관련 규정·약관·사례 (document + page + section)
    검증: "검색 결과가 실제로 이 issue와 관련된가?"
    ─────────────────────────
    왜 이 단계가 필요?
      - "우대금리 미적용"은 여러 규정 (금소법, 은행법, 약관)과 관련
      - 일반 검색은 고관련성 결과를 놓칠 수 있음
      - 다중 소스 (법령 + 약관 + 사례)를 조합해야 근거가 견고
    
    기술 선택: 
      - 벡터 검색 (ChromaDB): 의미 기반 검색 (약 95% 상위 5개 내 관련도 있음)
      - 키워드 검색 (전문용어 매칭): 정확도 100%
      - 메타데이터 필터 (상품·이슈·시행일): 오류 30% 감소
      - Hybrid: 벡터 점수 * 0.6 + 키워드 점수 * 0.4
    
    실패율 허용: <10% (관련 문서를 완전히 놓치는 경우)
    
    ↓
5. Logic Verification (규정 적용 검증)
    입력: 사실들 + 검색된 규정·약관
    출력: supported / unsupported / unknown (각각 근거 포함)
    검증: "판단이 규정에 부합하는가? 예외는 없는가?"
    ─────────────────────────
    왜 이 단계가 필요?
      - 검색된 규정을 무조건 적용하면 안 됨
      - "우대금리 미적용"이 규정 위반인지 확인하려면:
        ✓ 계약에 우대금리가 명시되었는가? (YES)
        ✓ 조건을 충족했는가? (UNKNOWN)
        ✓ 시행 시점에 이 규정이 유효했는가? (YES)
        ✗ 예외 사유가 있는가? (예: 선택약관)
      - 이 모든 것을 체계적으로 검증
    
    기술 선택: Claude API + Prompt Engineering 
               (각 규정의 요건·예외·적용 시점을 명시)
    
    신뢰도: confidence 스코어 (0~1) 부여
    
    ↓
6. Decision Gate (최종 판단)
    입력: verification 결과
    출력: proceed / amend / ask / hold
    검증: "이 판단이 사용자 보호를 최대화하는가?"
    ─────────────────────────
    판단 기준 (우선순위):
      1. hold (≥1개 고위험 신호) → 자동 전문가 검토로 이관
         - 명의도용 의심
         - 자격 조회 실패
         - 규정 충돌
      2. ask (≥1개 필수 사실 미확인) → 사용자에게 추가 정보 요청
         - "조건 충족 여부를 은행에 직접 확인하세요"
      3. amend (마스킹 필요 또는 서류 정리 필요) → 사용자 수정 후 재분석
         - "개인정보 XXX가지를 정리해주세요"
      4. proceed (충분한 근거 + 처리 가능) → 사용자에게 절차 제시
         - "이 근거로 은행 민원창구에 신청하세요"
    
    기술 선택: Rule-based (LLM 없음) 
               → 결정 기준이 명확해야 하고, 
                 투명성(interpretability)이 중요
    
    ↓
7. Content Scope Controller (민감정보 처리)
    입력: 최종 응답 텍스트 + 관련 문서
    출력: 마스킹된 응답 + 사용자 동의 필요 항목
    검증: "어떤 정보가 노출되었는가? 필요한 것인가?"
    ─────────────────────────
    마스킹 규칙 (문맥 기반):
      ✓ 계약 당사자(사용자) 정보: 노출 (근거 필요 시)
      ✗ 배우자·자녀 정보: 항상 마스킹
      △ 계좌번호: 거래 증빙이 필요하면 부분 노출 (끝 4자리)
      △ 주민번호: 법적 문서에서만 부분 노출 (연도만)
      ✗ 내부 직원명·조직: 항상 마스킹
    
    기술 선택: NER (Named Entity Recognition) + 규칙 기반
               → 미분류 시 사용자 확인 체크박스로 처리
    
    ↓
8. Response Composer (최종 응답 작성)
    입력: 모든 이전 단계 결과
    출력: 사용자 친화적 응답 (민원별 섹션)
    ─────────────────────────
    응답 구조:
      [민원 1] 우대금리 미적용
        1. 민원 요약
        2. 확인된 사실 (confidence 표시)
        3. 관련 규정 (인용 X, 설명 O)
        4. 판단 (supported/unsupported/unknown with 근거)
        5. 권장 다음 단계
        6. 필요 서류
        7. 개인정보 주의사항
      [민원 2] 우대금리 설명 부족
        [위와 동일 구조]
    
    기술 선택: Template + Claude API (설명 작성)
    
    검증: "근거 없는 법률 판단이 없는가?", "개인정보는 마스킹되었는가?"
```

이 데이터는 금융기관 콜센터에서 실제로 발생한 상담 내용을 기반으로, 상담 문맥을 반영한 질문–응답–후속질문 구조로 재구성한 Instruction Tuning 학습용 데이터다. 은행·보험·증권 3개 도메인의 상담 원천데이터 71,257건을 라벨링해 100,000건 규모의 학습 데이터로 구축했다.

### D.2 구축 목적 및 우리 파이프라인과의 연결

이 데이터의 원래 구축 목적은 "금융분야 고객상담 데이터를 기반으로 한 자동 주제 분류, 요약, 응답 생성 등 상담 서비스 고도화"다. 우리 파이프라인에서는 이 목적을 다음과 같이 재활용한다.

| 원 데이터의 라벨링 유형 | 우리 파이프라인에서의 활용처 |
|---|---|
| 주제 분류 (Instruction QA) | Case Builder Agent — 민원 분리 기준 학습·평가 (issue_type 분류) |
| 요약 | Response Composer — "쉬운 설명" 문체 학습 |
| 질문–응답–후속질문 구조 | Case Builder Agent 2단계(Focus 구조화) — 누락 정보 확인 질문 패턴 학습 |

이 데이터는 우리가 자체 제작한 시나리오 데이터(단일 75건·복합 75건, `ground_truth_subissues` 라벨 포함)와는 성격이 다르다. 자체 데이터는 **분리 정확도 평가**를 위한 정답셋이고, 이 콜센터 상담 데이터는 **실제 상담 문체와 질의응답 패턴을 학습**시키기 위한 대규모 보강 데이터다. 두 데이터는 서로 대체하지 않고 병행 사용한다.

### D.4 활용 시 확인이 필요한 사항

바로 학습에 투입하기 전에 아래 항목은 별도로 확인·보완이 필요하다.

- **개인정보 비식별화 여부**: 이 메타데이터에는 개인정보 마스킹·비식별 처리 여부가 명시되어 있지 않다. 실제 상담 원문이라면 계좌번호·성명·연락처 등이 포함되어 있을 가능성이 높으므로, Content Scope Controller 학습에 사용하기 전에 비식별 처리 여부를 원 데이터 제공처(하나은행 등)에 확인해야 한다.
- **라이선스 범위**: "구매" 데이터이므로, 이 라벨링 데이터를 우리 파이프라인 학습·평가에 활용하는 것이 구매 계약 범위에 포함되는지 확인이 필요하다. 특히 대회 제출용 공개 저장소(GitHub)에 원본 또는 파생 데이터를 포함시켜도 되는지는 별도 확인 사항이다.
- **도메인 불일치**: 위에서 언급했듯 이 데이터의 은행 카테고리 체계(대출문의, 이자/연체금액 등)와 우리 issue_type 체계(우대금리 미적용, 중도해지 수수료 안내 불일치 등)가 1:1로 매핑되지 않는다. 학습에 투입하기 전 카테고리 매핑표를 별도로 만들어야 한다.

### D.5 자체 데이터와의 관계 요약

```
자체 시나리오 데이터 (150건)          콜센터 상담 데이터 (원천 71,257 / 라벨링 100,000)
  용도: 분리 정확도 평가                 용도: 상담 문체·질의응답 패턴 학습
  특징: ground_truth 라벨 보유            특징: 실제 상담 문맥 기반, 대규모
  현재 상태: 확보·라벨링 완료             현재 상태: 확보 완료, 은행분야 우선 활용 검토
```

두 데이터셋은 평가 계획(PRD 11장)에서 서로 다른 역할을 맡는다 — 정확도를 "재는" 자체 데이터와, 모델을 "훈련시키는" 콜센터 데이터로 구분해서 평가 계획에 반영한다.
