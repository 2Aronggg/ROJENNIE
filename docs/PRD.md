# PRD: 금융소비자 보호 에이전트

## 1. 제품 개요

### 목적

사용자가 여러 금융 문제를 한 번에 설명해도 각각의 민원 사건으로 분리하고, 사실관계와 증빙을 정리하여 관련 규정·약관·사례를 근거로 이해하기 쉬운 해결 방안을 제시한다.

### 해결하려는 문제

- 사용자는 예금·투자상품의 금융 용어와 절차를 이해하기 어렵다.
- 하나의 문의에 여러 상품과 쟁점이 섞여 있어 단일 검색으로는 정확한 근거를 찾기 어렵다.
- 계약일, 사건일, 안내일, 금융회사 답변일이 달라 최신 사실을 놓치기 쉽다.
- 규정상 가능한 주장과 실제 제출 가능한 증빙을 구분하기 어렵다.
- 주민번호, 계좌번호, 거래내역 등 민감정보를 과도하게 제출할 위험이 있다.

## 2. 대상 사용자

1. 금융상품의 설명 부족, 이자·수수료·지급금액 오류를 겪은 개인
2. 금융회사 답변을 받았지만 다음 절차를 모르는 소비자
3. 민원 상담 전에 계약서와 증빙을 정리하려는 소비자
4. 전문가에게 전달할 사건 요약을 준비하는 사용자

## 3. MVP 범위

### 포함

- 예금·적금·펀드·ELS 민원
- 단일·복합 민원 분해
- 사건 그래프 기반 사실·증빙 정리
- 공통 법령 및 상품 문서 검색
- 규정 적용 요건, 예외, 부족한 사실 표시
- 제출 서류 체크리스트와 절차 안내
- 개인정보 마스킹 범위 제안
- `proceed / amend / ask / hold` 결정
- 근거 문서와 불확실성 표시

### 제외

- 금융회사·기관에 대한 자동 민원 제출
- 사용자를 대신한 계약 변경, 결제, 이체
- 규정 근거 없는 법률적 승소 보장
- 실제 분쟁조정 사례 기반 답변: 원문 수집 전까지 제한

## 4. 사용자 시나리오

### 시나리오 A: 단일 예금 민원

사용자: “정기예금을 해지하려는데 영업점 시스템 점검 때문에 3일째 처리되지 않고 있습니다.”

처리:

1. `Issue Splitter`가 `예금 / 계약해지 지연`으로 분류한다.
2. `Focal Builder`가 focal을 예금계약과 해지 요청으로 지정한다.
3. 계약·예금거래기본약관·상품설명서에서 해지 절차와 제한 사유를 검색한다.
4. 실제 시스템 장애인지, 본인확인 서류 미비인지 추가 사실을 확인한다.
5. 확인된 내용에 따라 처리 가능한 절차와 제출할 기록을 안내한다.

### 시나리오 B: 복합 민원

사용자: “예금에서 12만 원을 인출하려는데 계속 거부되고, 적금 우대금리 문의도 10일째 확인 중이라고만 합니다.”

기대 결과:

- 민원 1: 예금 인출 제한
- 민원 2: 적금 우대금리 설명·민원 처리 지연
- 두 민원을 별도로 검색·검증한다.
- 공통 사실은 공유하되, 규정 근거·필요 서류·접수 절차는 섞지 않는다.
- 최종 답변에서 민원별 상태와 다음 행동을 구분한다.

### 시나리오 C: 고위험 민원

사용자: “내가 신청하지 않은 펀드 거래가 있고 금융회사에서는 본인 인증이 완료됐다고 합니다.”

기대 결과:

- `명의도용 / 비인가 거래`로 분류한다.
- 거래내역, 인증 기록, 금융회사 답변을 focal로 연결한다.
- 단정적인 환급 약속을 하지 않는다.
- 추가 확인과 즉시 보호 조치를 안내하고 `hold` 또는 전문가 검토로 보낸다.

## 5. 처리 아키텍처

```text
사용자 입력
    ↓
1. Issue Splitter
    ↓
2. Focal Builder
    ↓
3. Case Graph + Fact Resolver
    ↓
4. Hybrid Retriever
    ↓
5. Logic Verification
    ↓
6. Decision Gate
    ├─ proceed
    ├─ amend
    ├─ ask
    └─ hold → Human Review
    ↓
7. Content Scope Controller
    ↓
8. Response Composer
```

사용자에게 보이는 핵심 에이전트는 5개로 유지합니다. Case Graph, Fact Resolver, Decision Gate, Content Scope Controller는 독립 LLM 에이전트가 아니라 공통 처리 모듈입니다.

## 6. 에이전트별 구현 요구사항

### 6.1 Issue Splitter

입력 문장에서 상품명이 아니라 독립된 문제와 요구 조치를 추출한다.

출력 필드:

```json
{
  "issue_id": "issue_001",
  "product": "적금",
  "issue_type": "우대금리설명부족",
  "text_span": "우대금리 조건을 충분히 안내받지 못했다",
  "requested_remedy": "우대금리 적용 근거와 조정 요청"
}
```

같은 계약·같은 사건·같은 해결 조치에 속하면 합치고, 규정·증빙·접수 경로가 다르면 분리한다.

### 6.2 Focal Builder

각 민원의 중심 대상과 처리 대상을 확정한다.

```json
{
  "focal": {
    "type": "notice",
    "ref": "interest_change_notice"
  },
  "target": {
    "subject": "금융회사",
    "action_target": "금융회사 민원창구"
  },
  "facts": [],
  "missing_facts": [],
  "evidence_refs": [],
  "risk_flags": []
}
```

문서 입력 순서를 최신성으로 사용하지 않는다. 사건 발생일, 규정 시행일, 문서 작성일, 사용자 수신일, 시스템 입력일을 구분한다.

### 6.3 Hybrid Retriever

검색은 다음 세 묶음을 결합한다.

1. 공통 금융소비자 규정
2. 상품·쟁점별 약관과 상품설명서
3. 분쟁조정·민원 사례

현재 저장소에는 1·2와 자체 시나리오가 있으며, 3의 공식 원문은 추가 수집 대상이다.

문서 메타데이터:

```json
{
  "doc_id": "law_fsc_001",
  "doc_type": "law",
  "product": ["공통"],
  "issue_types": ["설명의무위반"],
  "source": "국가법령정보센터",
  "effective_from": "2026-01-02",
  "effective_to": null,
  "page": 12,
  "section": "제X조"
}
```

검색 결과는 반드시 문서명·페이지·조항 또는 섹션을 반환한다.

### 6.4 Logic Verification

검색 결과를 사실관계에 적용하되, 결론을 다음 세 단계로 나눈다.

- `supported`: 문서와 증빙이 요건을 뒷받침함
- `unsupported`: 확인된 사실이 요건과 맞지 않음
- `unknown`: 핵심 사실이나 증빙이 부족함

각 판단에는 적용 요건, 해당 사실, 근거 문서, 예외, 부족한 점을 함께 기록한다.

### 6.5 Response Composer

복합 민원은 반드시 민원별 섹션으로 답한다.

```text
1. 민원 요약
2. 현재 확인된 사실
3. 관련 규정·약관·사례
4. 판단: 확인됨 / 확인 불가 / 추가 확인 필요
5. 권장 다음 단계
6. 제출 서류
7. 개인정보 주의사항
8. 전문가 검토 필요 여부
```

규정 원문을 길게 복사하지 않고 쉬운 설명과 근거 위치를 함께 제공한다.

## 8. API 초안

MVP에서 필요한 API는 세 개면 충분하다.

| Method | Path | 역할 |
|---|---|---|
| `POST` | `/api/v1/cases/analyze` | 문의를 분석하고 민원별 결과 반환 |
| `GET` | `/api/v1/cases/{case_id}` | 사건 그래프·근거·진행 상태 조회 |
| `POST` | `/api/v1/cases/{case_id}/review` | Human Review 결과 반영 후 재생성 |

외부 기관 자동 제출 API는 MVP에서 만들지 않는다.

## 9. 클라이언트 요구사항

- 문의 입력창과 파일 첨부
- 복합 문의에서 민원별 카드 또는 React Flow 상태 표시
- 민원별 focal, 상품, 쟁점, 결정 상태 표시
- 근거 문서의 페이지·조항 상세 패널
- 부족한 사실과 제출 서류 체크리스트
- 개인정보 마스킹 결과와 사용자 확인 항목
- `hold` 상태에서 전문가 검토 대기 표시

## 10. 비기능 요구사항

- 답변의 모든 규정 판단은 검색 근거를 가져야 한다.
- 근거 문서의 시행일이 사건일·계약일에 유효한지 확인한다.
- 개인정보는 최소 수집·최소 표시한다.
- 확인되지 않은 사실은 사실처럼 출력하지 않는다.
- 사용자 요청과 하위 민원 간 근거가 섞이지 않아야 한다.
- 모델이 만든 판단과 원문 근거를 분리 저장한다.

## 11. 평가 계획

현재 자체 데이터의 `complex_issue_75.json`은 `ground_truth_subissues`를 제공하므로 분해 평가에 사용한다.

초기 평가 항목:

| 항목 | 평가 방법 |
|---|---|
| 민원 분해 | 복합 75건의 하위 민원 수·상품·쟁점·참조 ID 비교 |
| focal 추출 | 계약·거래·안내문·답변서 등 중심 대상 정확도 |
| 검색 | 근거 문서의 상품·쟁점·시행일 일치 여부 |
| 검증 | 요건·예외·미확인 사실 누락 여부 |
| 답변 | 민원별 절차·서류·주의사항 포함 여부 |
| 안전성 | 명의도용·개인정보 민원이 `proceed`로 과도하게 통과되지 않는지 확인 |

초기 목표는 복합 75건의 하위 민원 exact match 80% 이상, 근거 없는 규정 단정 0건으로 둔다. 실제 목표는 평가셋 검토 후 조정한다.

## 12. 데이터 리스크

- 공식 분쟁조정 사례 원문이 없어 사례 RAG 품질을 평가할 수 없다.
- 파일명에 표시된 날짜만으로 현행 법령 여부를 판단하면 안 된다.
- `자본시장법 ... 20260804` 파일처럼 현재 기준으로 시행일 확인이 필요한 문서가 있으므로 `effective_from` 검증이 필수다.
