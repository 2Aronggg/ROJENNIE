# Hybrid Retriever Rules

## 목적

구조화된 민원 정보로 공통 규정, 상품 문서, 사례를 검색하고 근거 위치를 반환한다.

Focal Builder가 "어떤 자료를 봐야 하는가(focal)"와 "이 사실이 무엇인가(사실 기록)"를 구조화했다면, Hybrid Retriever는 그 구조화된 정보를 가지고 "이 사실을 판단할 근거가 어디에 있는가"를 찾는 단계다. 이 단계는 근거 문서를 찾아서 위치(문서명·페이지·조항)까지 정확히 반환하는 데서 끝난다. 찾은 근거가 이 민원에 유리한지 불리한지, 요건을 충족하는지는 판단하지 않는다 — 그 판단은 다음 단계인 Logic Verification의 몫이다. Hybrid Retriever가 스스로 판단까지 해버리면, 검색 과정에서 이미 결론이 왜곡될 위험이 있기 때문에 이 경계를 분리해서 지킨다.

## 검색 순서

```text
공통 금융소비자 규정
→ 상품·쟁점별 약관과 상품설명서
→ 공식 분쟁조정·민원 사례
```

이 순서는 우선순위이지 배타적 선택이 아니다. 공통 규정에서 먼저 원칙을 확인하고, 그다음 이 민원의 구체적인 상품에 적용되는 약관·상품설명서로 좁혀 들어가며, 마지막으로 유사 사례가 있는지 확인한다. 세 계층은 서로 다른 성격의 근거이므로 하나가 다른 하나를 대체하지 않는다 — 공통 규정만 찾고 상품 문서를 생략하거나, 반대로 상품 문서만 찾고 공통 규정을 생략하지 않는다.

**공통 규정과 상품 문서가 서로 다른 결론을 보이면 둘 다 반환하고 Logic Verification으로 넘긴다.** 예를 들어 공통 규정(금소법)은 설명의무를 강하게 요구하는데, 상품 약관에는 예외 조항이 있는 경우, Hybrid Retriever는 어느 쪽이 우선하는지 스스로 정리하지 않는다. 둘 다 근거로 반환하고, 그 충돌을 해석하는 일은 다음 단계에 넘긴다.

현재 시스템에는 공통 규정과 상품 문서(1·2계층)가 색인되어 있고, 3계층(공식 분쟁조정 사례 원문)은 아직 확보되지 않았다. 3계층 자료가 없는 상태에서는 1·2계층까지만 검색하고, 사례 근거가 필요한 상황이면 `evidence_insufficient`로 표시한다 (아래 근거 규칙 참고).

## 쿼리 구성

검색어는 다음 정보를 조합한다.

```text
issue_type + product + focal_type + disputed_fact + relevant_date
```

예: `적금 + 우대금리설명부족 + 상품설명서 + 우대금리 조건 + 가입일`

각 구성 요소는 Focal Builder가 이미 구조화해둔 필드에서 그대로 가져온다 — Hybrid Retriever가 새로 해석하거나 추측해서 채우지 않는다.

- `issue_type`: Issue Splitter가 분류한 값 그대로 사용한다.
- `product`: 상품명. 다만 상품명만으로 검색 범위를 과도하게 좁히지 않는다 — 상품명이 정확히 일치하지 않아도 같은 상품군의 공통 규정은 검색 대상에 포함한다.
- `focal_type`: Focal Builder가 채택한 focal 후보(계약서·약관, 변경 안내 등)를 그대로 반영해, 어떤 종류의 문서를 우선 찾을지 좁힌다.
- `disputed_fact`: 사실 기록에서 다툼이 있는 값(예: "우대금리 조건"). `conflicts_with`가 있는 필드는 특히 검색 우선순위를 높인다.
- `relevant_date`: 사건일(`event_date`) 기준으로 검색한다. `recorded_date`를 기준으로 검색하면 그 사실이 기록된 시점의 규정을 잘못 찾아올 수 있으므로 반드시 `event_date`를 쓴다.

**KB 정기예금 예시 (issue_001, 우대금리 미적용) 쿼리 구성**
```text
정기예금 + 우대금리미적용 + 계약서·약관 + 우대금리 3.5%/2.1% + 2025-03-10(가입일)
```

## 메타데이터 필터

- 상품
- 쟁점 유형
- 문서 유형
- 출처
- 시행일
- 페이지·섹션

메타데이터 필터는 벡터 검색만으로 걸러내기 어려운 조건들을 명시적으로 제한하는 역할을 한다. 특히 시행일 필터는 "의미상 관련 있어 보이지만 이 사건 시점에는 적용되지 않는 규정"을 걸러내는 데 필수적이다. 현재 색인된 문서는 다음 메타데이터 스키마를 따른다(PRD 6.3과 동일):

```json
{
  "doc_id": "law_fsc_001",
  "doc_type": "law",
  "product": ["공통"],
  "issue_types": ["설명의무위반"],
  "source": "국가법령정보센터",
  "effective_from": "2026-01-02",
  "effective_to": null,
  "page": 12,
  "section": "제X조"
}
```

이 데이터는 이미 벡터 DB(ChromaDB)에 색인되어 있으므로, Hybrid Retriever는 새로 문서를 파싱하지 않고 이 메타데이터를 필터 조건으로만 사용한다. `product`, `issue_types` 필터는 관련 없는 문서를 1차로 걸러내고, `effective_from`/`effective_to` 필터는 아래 근거 규칙의 시행일 제한을 실제로 적용하는 수단이다.

## 근거 규칙

- **검색 결과마다 `doc_id`, 문서명, 페이지·섹션, 적용 시점을 반환한다.** 근거 없이 결론만 반환하는 결과는 허용하지 않는다 — 어떤 문서의 몇 조, 몇 페이지에서 나온 근거인지 항상 함께 반환해야 다음 단계에서 검증하고, 최종 답변에서 사용자에게 근거 위치를 제시할 수 있다.
- **자체 제작 민원 JSON·CSV는 법령 근거로 검색하지 않는다.** `complex_issue_75.json` 같은 자체 시나리오 데이터는 Issue Splitter 평가용 데이터이지 근거 문서가 아니다. 이 데이터가 검색 결과에 섞여 들어가면 실제 규정이 아닌 것을 근거처럼 반환하는 오류가 생기므로, 검색 대상 자체에서 제외한다.
- **시행일이 사건일 이후인 규정은 현재 사건의 근거로 사용하지 않는다.** `effective_from`이 `event_date`보다 늦은 문서는 그 사건 시점에 존재하지 않았던 규정이므로 근거가 될 수 없다. 이는 Focal Builder가 강조한 `event_date`/`recorded_date` 구분을 검색 단계에서 실제로 적용하는 규칙이다 — 아무리 의미상 관련도가 높아도 시행일 조건을 통과하지 못하면 근거로 채택하지 않는다.
- **결과가 없으면 검색 실패가 아니라 `evidence_insufficient`로 표시한다.** 검색어를 재구성해도 관련 문서가 없는 경우, 이를 오류로 처리하거나 조용히 빈 배열만 반환하지 않는다. `evidence_insufficient`로 명시적으로 표시해서, 다음 단계가 "근거가 없다"는 사실 자체를 판단에 반영할 수 있게 한다. 특히 3계층(공식 분쟁조정 사례)처럼 아직 데이터가 없는 영역은 이 표시가 나올 가능성이 높다는 점을 감안한다.

## 판단 예시

**입력** (Focal Builder에서 넘어온 issue_001의 focal + 사실 기록)
```json
{
  "issue_id": "issue_001",
  "issue_type": "우대금리 미적용",
  "product": "정기예금",
  "focal": ["계약서·약관", "거래내역·계산서", "우대금리·수수료 변경 안내"],
  "facts": [
    { "field": "interest_rate_contracted", "value": "3.5%", "event_date": "2025-03-10" },
    { "field": "interest_rate_applied", "value": "2.1%", "event_date": "2026-06-01" }
  ]
}
```

**검색 순서 대입**
| 계층 | 검색 대상 | 결과 |
|---|---|---|
| 1. 공통 규정 | 금소법 설명의무 조항 | `law_fsc_001`, 제10조, 시행일 2026-01-02 (사건일 2025-03-10 계약 체결 시점보다 늦음 → 계약 체결 당시 규정 별도 확인 필요) |
| 2. 상품 문서 | KB 우량우대예금 약관, 우대금리 변경 안내 | `prod_deposit_001`(약관, 시행 2025-01-01~), `notice_2026_003`(변경 안내, 시행 2026-01-05~) |
| 3. 분쟁조정 사례 | (미확보) | `evidence_insufficient` |

**메타데이터 필터 적용**
- `product`: 정기예금
- `issue_types`: 우대금리미적용, 설명의무위반
- `effective_from` ≤ 2026-06-01(사건일) 또는 계약 체결 시점(2025-03-10) 기준으로 이원 검색

**반환 형태**
```json
{
  "evidence": [
    { "doc_id": "prod_deposit_001", "title": "KB 우량우대예금 약관", "page": 4, "section": "제3조 우대금리", "effective_from": "2025-01-01" },
    { "doc_id": "notice_2026_003", "title": "우대금리 변경 안내", "page": 1, "section": null, "effective_from": "2026-01-05" }
  ],
  "case_law_evidence": "evidence_insufficient"
}
```

이 반환값까지가 Hybrid Retriever의 역할이다. 두 문서가 서로 다른 금리(3.5% vs 2.1%)를 언급하고 있다는 사실이나, 이 변경이 정당한지는 여기서 정리하지 않는다 — 그 해석은 Logic Verification 단계로 넘어간 뒤의 일이다.
